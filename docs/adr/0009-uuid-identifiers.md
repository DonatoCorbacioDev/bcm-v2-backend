# ADR-0009: UUIDs for every record identifier, stored as CHAR(36), version 7 for new rows

**Status:** Accepted
**Date:** 2026-11-09

## Context

Every table uses an auto-increment `BIGINT` primary key, and those numbers appear in URLs,
request bodies, JWT claims (`orgId`), the backend→ML claims ([ADR-0008](0008-asymmetric-internal-claims.md))
and file storage paths.

Object-level authorization does not depend on them being secret: since the OWASP API1 work of
2026-11-09 every lookup is scoped to the caller's organization and, where it applies, to the
assigned manager; a foreign or missing ID answers 404 either way; and the BOLA matrices
(`docs/BOLA_TEST_MATRIX.md`) plus the two-organization HTTP check prove it. So guessing an ID
gains nothing today.

What sequential IDs still give away, and what OWASP API1 means by "prefer random and
unpredictable values as GUIDs for records' IDs", is:

- **Volume across tenants**: the ID of a record a customer just created tells them roughly how
  many records exist in the whole system, and two IDs taken a week apart tell them the growth
  rate. For a multi-tenant product that is business information about other customers.
- **A second line of defence**: if a future change ever drops a tenant or ownership check,
  sequential IDs make the hole exploitable by counting; random IDs make it far harder to find
  anything to request.

## Decision

1. **Every identifier becomes a `java.util.UUID`**, in all tables (tenant data, users, tokens,
   roles, join tables), in the API, the frontend, the ML service, the demo data and the tests.
   No mixed state: a partial migration would leave two ID styles to reason about forever.
2. **Stored as `CHAR(36)` in MySQL** (canonical text form), via
   `hibernate.type.preferred_uuid_jdbc_type=CHAR`.
3. **New rows get a UUIDv7**, generated by the application. Version 7 is time-ordered, so
   inserts stay close to the end of each index and the existing "newest first, ID as tie-breaker"
   orderings keep meaning "newer first". Rows that exist at migration time get a UUID assigned
   by the migration; their order among themselves is kept by `created_at`-style columns where
   the code needs it, and those orderings are reviewed one by one.
4. **The database migration is generated, not hand-written**: a script reads the real V54
   schema from `information_schema` and emits the migration (new UUID columns, twin columns for
   every foreign key filled through joins, then constraints, primary keys, unique keys and
   indexes recreated). It is proven by an integration test on real MySQL and by a full
   rehearsal on a restored production backup before it ships.
5. **One release** for backend, frontend and ML, in a short maintenance window, after a backup.
   Rollback is "restore the backup and the previous images"; there is no down-migration.
6. **The public demo organization gets a fixed, documented UUID** used by the seed, the nightly
   reset and the docs, instead of `3`.
7. A path variable that is not a valid UUID answers **400**; a valid UUID that is missing or
   belongs to someone else keeps answering **404**.

## Alternatives considered

- **Keep sequential IDs and document the residual risk.** Cheapest (about an hour) and defensible,
  since every access is already authorized. Rejected by an explicit product decision: the
  cross-tenant volume leak is real, and OWASP's recommendation is cheap to satisfy for new
  projects and only gets more expensive the longer it waits.
- **Add a separate public UUID column and keep `BIGINT` keys internally.** Gives the same external
  protection with a smaller database change, but every endpoint, DTO and the frontend still
  change, and the code then carries two identifiers per record forever (which one does this
  method take?). Rejected in favour of a single identifier.
- **`BINARY(16)` storage.** Half the size of `CHAR(36)` and the usual choice at large scale.
  Rejected here because BCM's volumes make the difference negligible, while plain text keeps the
  ops scripts (bash + `mysql`), the demo seed SQL, the ML service's SQLAlchemy models and
  everyday debugging simple. Revisit only if table sizes ever make index size matter.
- **UUIDv4 (fully random) for new rows.** Equally unguessable, but random insert positions
  fragment the indexes and lose the "ID order roughly follows time" property the code relies on
  as a tie-breaker. Version 7 keeps both.
- **MySQL `UUID()` with `UUID_TO_BIN(…, 1)` (time-swapped v1).** Ties identifier generation to the
  database and to a byte-swapping convention the application would have to mirror. Generating
  v7 in the application is simpler and portable to H2 in tests.
- **Per-organization sequences.** Would hide cross-tenant volume but not the per-tenant one, and
  needs custom generators on every table. Not worth it compared with UUIDs.

## Consequences

- **Positive:** record IDs reveal nothing about other customers and cannot be enumerated; a
  future authorization slip is much harder to exploit. Closes the last OWASP API1 recommendation.
- **Negative:** the largest single change so far: about 27 tables and 108 foreign keys, every DTO,
  controller and repository signature, the frontend types and routes, the ML models, the demo
  seed and a large share of the tests. A planned maintenance window is needed. Links users
  bookmarked with old numeric IDs (for example `/contracts/123`) stop working.
- **Neutral:** files already uploaded keep their stored paths (the full path is saved in
  `storage_path`); new files are stored under the organization's UUID, so deleting an
  organization must clean both its old numeric folder and its new one. The ML result cache is
  emptied at release.
