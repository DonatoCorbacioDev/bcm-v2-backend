# Security overview

This document summarizes the current threat model and the concrete steps required before
running BCM in production. It reflects the state of the codebase as audited on 2026-11-09
(OWASP API Top 10, API1 object-level authorization),
not aspirational claims — update it whenever a control changes.

For personal-data-specific obligations (GDPR: data categories, sub-processors,
retention, data-subject rights), see `docs/GDPR.md` — this document covers
the technical security controls that back article 32.

**Where the real boundary crossings are, and what's missing:**

1. **Browser → Frontend**: the only crossing with no authentication by design (login page must be reachable). CSP with a per-request nonce is the main control (`middleware.ts`).
2. **Browser → Backend**: every state-changing or data-reading request crosses this boundary directly — the frontend is a single-page app that calls the backend API client-side (`NEXT_PUBLIC_API_URL`), not through a server-side proxy that could otherwise sit in front of it as a second choke point. JWT Bearer token + `HttpOnly`/`Secure`/`SameSite=Strict` refresh cookie (a foreign `Origin` refused with 403 by CORS) scoped to `/auth` are the controls; see the table below for what's not yet covered (distributed rate limiting).
3. **Backend → MySQL**: *not* a zero-trust boundary today — no network-level auth beyond the DB password, and the database has no idea what tenant a query is scoped to. All isolation is enforced in application code (`TenantContext` + explicit `findByOrganization_Id`-style queries), verified against a real database by `CrossTenantIsolationIT` and `BolaJwtMySQLIT` (signed JWTs, committed rows; see `docs/BOLA_TEST_MATRIX.md`). If that discipline ever lapses on a single query, MySQL itself won't stop it — this is the single most consequential trust assumption in the whole system.
4. **Backend → ML**: the one internal hop that *does* carry its own credential (`X-Internal-Api-Key`), because the ML service is a separate deployable with its own attack surface, not just an internal library call.
5–7. **ML/Backend → Ollama, ML → MySQL**: Ollama has no auth at all, because it never leaves the same trust zone (Docker network / host loopback). The ML service reaches MySQL through its own account (`bcm_ml_ro`, created by `bcm-v2-docker/ops/mysql/create-ml-readonly-user.sh`) with `SELECT` on `contracts`, `counterparties` and `financial_values` only: it cannot write anything, nor read users, password hashes or 2FA secrets (in production since 2026-11-09). Acceptable *only* as long as that network boundary holds — the moment any of `mysql`, `ml`, or Ollama's port is published to the host or a public interface, this whole zone's "same trust zone, no auth needed" assumption breaks. `docker-compose.yml` already binds all host-published ports to `127.0.0.1` for exactly this reason; the production checklist below has the equivalent items for a real deployment.

### Asset / threat matrix

| Asset | Threat | Current mitigation | Residual risk |
|---|---|---|---|
| Tenant data (contracts, documents, invoices) | Cross-tenant data leak | `TenantContext` (populated from the JWT `orgId` claim by `JwtAuthenticationFilter`) scopes every repository query in services. Fails closed (2026-11-09): a token without `orgId` authenticates nobody, and a service reached without an organization throws `MissingTenantException` (403) via `TenantContext.require()` instead of querying across organizations. Scheduled jobs (`MonthlyReporter`, `RiskScoreRefresher`) never rely on an empty context: they iterate the organizations and pass each id explicitly. Covered by `CrossTenantAccessTest`, `BolaAuthorizationMatrixTest` and `BolaJwtMySQLIT` | MySQL itself does not enforce tenancy (see trust boundary 3): a new query written without the organization filter would be stopped only by review and the BOLA matrices, not by the database |
| Single objects inside a tenant | A plain manager reading or changing a colleague's contract; a child resource (document, invoice, history entry) addressed through another contract; a client-supplied ID in a request body | `ContractAccessGuard` checks tenant scope, then assignment, on every contract-scoped endpoint; child resources are looked up by both their own ID and the parent contract's; IDs in request bodies (contract, type, area, manager) are resolved only inside the caller's organization; create endpoints discard the client-supplied `id`, so `save` can never merge an existing row. Expected results (404 for missing or foreign, 403 for a colleague's contract) are listed in `docs/BOLA_TEST_MATRIX.md` and enforced by `BolaAuthorizationMatrixTest` (H2) and `BolaJwtMySQLIT` (real MySQL) | Workflow approvers may read a colleague's workflow in the same organization, by design |
| Properties of an object (OWASP API3) | Mass assignment: a request setting a field its caller may not set (a verified IBAN, a financial value's source, a contract's approval stage, a user's 2FA, the plan); a response carrying a field its reader may not see; a history entry signed in a colleague's name or backdated | Every endpoint takes and returns DTOs, never entities. Read-only fields are ignored on write: `verifiedIban`/`verifiedBic` only through the explicit confirmation, `source` always `MANUAL` on manual writes, the workflow stage derived by the server, a client `id` discarded on creation, `twoFactorEnabled` and `subscriptionTier` never read from a request. | Functions by role (OWASP API5) | A manager calling an administrator's function; a new endpoint shipped without a role; an approver approving their own contract; any logged-in user reading the platform's metrics | Denied by default: every endpoint declares `@PreAuthorize`, and `FunctionLevelAuthorizationTest` reads every registered endpoint and fails on one without, unless it is on a short list of public or own-account endpoints with the reason; the same test checks a manager gets 403 on the administrator's functions. | Sensitive business flows (OWASP API6) | The same invoices paid twice by a double click or two colleagues at once; a mailbox flooded with registration codes by starting the sign-up over and over; abuse that is refused but that no one ever sees | Payments: the invoices of a SEPA batch are locked while it is created (`SELECT ... FOR UPDATE`, `ElectronicInvoiceRepository`), so a simultaneous request waits and then finds them paid; an invoice already in a batch is refused, an IBAN other than the verified one blocks the payment, the same FatturaPA can't be uploaded twice (V41). - [x] Generate a fresh `JWT_SECRET` (≥256 bits, Base64) per environment — never reuse the dev/example value. Production: set, 64 characters (secrets check, 2026-11-09).

Production: `403` from outside (2026-11-09).
- [x] Rotate or disable the default admin account seeded by `V4__create_admin_user.sql` (already neutralized by `V14`, but confirm before going live with a fresh database) — the second command of the check below. Production: `0` enabled `admin` accounts on the V4 hash (2026-11-09).
- [x] Run the production secrets check below on the VM, from `bcm-v2-docker`, after every change to the secrets or the environment (last run 2026-11-17: all as expected; `STRIPE_WEBHOOK_SECRET` empty with checkout disabled, to set before enabling payments). It prints only names, `SET`/`EMPTY`/`MISSING`, lengths and permissions, never a value, so its output is safe to paste:

  ```bash
  docker exec bcm-backend sh -c 'for v in JWT_SECRET JWT_SECRET_PREVIOUS TOTP_ENCRYPTION_KEY DB_APP_PASSWORD MAIL_PASSWORD ML_INTERNAL_API_KEY ML_CLAIMS_PRIVATE_KEY INTERNAL_ADMIN_API_KEY STRIPE_SECRET_KEY STRIPE_WEBHOOK_SECRET; do f=/run/secrets/$v; if [ ! -f "$f" ]; then echo "$v MISSING"; else n=$(tr -d "\n" < "$f" | wc -c); if [ "$n" -gt 0 ]; then echo "$v SET ($n chars)"; else echo "$v EMPTY"; fi; fi; done; for v in SPRING_PROFILES_ACTIVE FRONTEND_BASE_URL BCM_DEMO_LOCKED_USERNAME; do if [ -n "$(printenv "$v")" ]; then echo "$v SET"; else echo "$v MISSING"; fi; done'
  ```

## Secret rotation and revocation

Rotate a secret when it may have leaked (revoke at once), when someone who
knew it leaves, and otherwise once a year. Every secret is a file,
`bcm-v2-docker/secrets/<NAME>` on the VM; change it there, never in Git, and
take a backup first. Write a new value without printing it or putting it on
a command line, from `bcm-v2-docker`:
`openssl rand -base64 48 | tr -d '\n' | (source ops/secrets/lib.sh && secret_write JWT_SECRET)`,
or, for a value you type: `read -rs v && printf '%s' "$v" | (source ops/secrets/lib.sh && secret_write NAME); unset v`.
"Recreate" means
`docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-deps <service>`:
a running container keeps reading the value it started with until then.
After any change, run the secrets check above.

| Secret | How to rotate | Effect on users | How to confirm the old one is dead |
|---|---|---|---|
| `JWT_SECRET` (signs access and two-factor step tokens) | Generate a new key (`openssl rand -base64 48`). Copy `secrets/JWT_SECRET` into `secrets/JWT_SECRET_PREVIOUS` (`cat secrets/JWT_SECRET | (source ops/secrets/lib.sh && secret_write JWT_SECRET_PREVIOUS)`), write the new key to `secrets/JWT_SECRET`; recreate `backend`. After 15 minutes (the longest token lifetime) empty `secrets/JWT_SECRET_PREVIOUS` (`: | (source ops/secrets/lib.sh && secret_write JWT_SECRET_PREVIOUS)`) and recreate again. If the key leaked, skip `JWT_SECRET_PREVIOUS`: every access token dies at once. Before the first rotation, check the log of the start with `TOTP_ENCRYPTION_KEY` said "0 failed" | None: refresh tokens are random values stored hashed, not signed, so browsers get a new access token silently. With the leak path, an open page does one extra refresh | A token signed before the rotation gets `401` once `JWT_SECRET_PREVIOUS` is empty (`JwtKeyRotationTest`) |
| `TOTP_ENCRYPTION_KEY` (two-factor secrets at rest) | Not rotatable in place: changing it makes every stored secret unreadable. If it leaked together with the database, clear the two-factor columns of every user, set a new key (`ops/secrets/create-totp-encryption-key.sh` after deleting `secrets/TOTP_ENCRYPTION_KEY`), recreate `backend`; each admin sets 2FA up again at the next login. Alone, without the database, the key reveals nothing | Every admin with 2FA sets it up again | The old authenticator app's codes are refused |
| `DB_APP_PASSWORD` (backend runtime account) | `bash ops/mysql/rotate-password.sh app` (MySQL's dual password: the old one keeps working), recreate `backend` (`up -d --no-deps backend`), then `bash ops/mysql/rotate-password.sh app --discard-old` | None | After the discard, the old password is refused |
| `ML_DB_PASSWORD` (ML read-only account) | `bash ops/mysql/rotate-password.sh ml` (rewrites `secrets/ML_DB_URL` too), recreate `ml`, then `bash ops/mysql/rotate-password.sh ml --discard-old` | None | As above, for the ML account |
| `DB_PASSWORD` (owner account, the `migrate` container only) and `DB_ROOT_PASSWORD` | `bash ops/mysql/rotate-password.sh owner` (read by `migrate` at the next deploy, nothing to recreate) or `bash ops/mysql/rotate-password.sh root`, then recreate `mysql` (the ops scripts read root's file there; the healthcheck needs no password). `ops/mysql/check-privileges.sh` reports any password older than a year | A few seconds of restart | Login with the old password is refused |
| `ML_INTERNAL_API_KEY` (backend) = `INTERNAL_API_KEY` (ML) | `openssl rand -hex 32`; set the same value on both, recreate `backend` and `ml` together | ML features degrade for the seconds between the two | A call to the ML service with the old key is refused |
| `ML_CLAIMS_PRIVATE_KEY` (backend) / `INTERNAL_CLAIMS_PUBLIC_KEY` (ML) | New pair from `InternalClaimsKeyGenerator`; private half to the backend, public half to ML, recreate both together | As above | ML refuses claims signed with the old private key |
| `INTERNAL_ADMIN_API_KEY` | `openssl rand -hex 32`, recreate `backend`; empty disables the endpoints (`404`) | None | `X-Internal-Admin-Key` with the old value is refused on `127.0.0.1:8090` |
| `MAIL_PASSWORD` (Gmail app password) | Revoke it in the Google account, create a new app password, recreate `backend` | Emails wait for the restart | The Google account lists only the new one |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Roll the key and the webhook signing secret in the Stripe Dashboard, recreate `backend` (checkout is disabled today) | None while checkout is off | Stripe shows the old key as expired |
| Backup key (`age`, private half offline only) | `age-keygen` a new pair, put the new public key in `ops/backup/backup-recipient.pub`, commit. Keep the old private key as long as backups encrypted to it are kept | None | New backups do not decrypt with the old key |
| `demo_admin` password (`~/.bcm_demo_admin_pw`, used only by the nightly demo reset) | Change it in the app, write the new one to the file (`600`) | None | Login with the old password is refused |
| SSH key of the VM | Add the new public key to `~/.ssh/authorized_keys`, test it, remove the old line | None | The old key is refused |

## Known limitations (won't fix without explicit need)

- **The public demo's internal admin signs in without 2FA** (2026-11-11). Every other ADMIN must set it up before the first session; `BCM_2FA_EXEMPT_USERNAMES` lists the exceptions, and production lists only `demo_admin`: the nightly demo reset signs in as it with a password, it administers an organization of made-up data, and its password exists only on the server, never in the interface. An admin who loses the phone uses a recovery code; without one, the 2FA columns of that user are cleared in the database and the next login asks for a new setup. Turning 2FA off (with a code) is how an admin changes phone: the session ends and the next login asks for the setup again. Turning it on again in a session is refused while it is on: replacing the secret used to switch it off without a code.
- **Organization sign-up tells whether a username or an email is taken** ("Username già esistente", "Email già in uso"), by choice: the person has to know to pick another one, and hiding it would need a decoy registration that behaves the same through resend and confirm. Limited by the rate limiter on `/organizations/register*`. The password reset, where hiding it costs nothing, does not tell.
- **The `verification_token` table is no longer written** since the public sign-up was removed. It stays, with its entity and repository, because organization purge and the test cleaner still delete its rows; dropping it needs a migration of its own.
- **Deliberate null-organization paths** remain only where no tenant request exists: invitation acceptance (`UserService.completeInvite`, unauthenticated by nature, resolved through the invite token), notifications created by background jobs (`NotificationService.createForUser`) and the ML refresh jobs (`MlProxyService` `fetch*Raw`). None of them is reachable from a tenant HTTP request without an organization.
